# 库存查询系统 - 产品需求文档

## Overview
- **Summary**: 构建一个库存查询系统的 Web 端。管理员在后台上架物品、管理分类与账号、执行出入库并查看流水；普通用户在前台查询库存。后续需适配微信小程序查询端。
- **Purpose**: 提供一套可追溯的库存管理与查询能力，管理员掌握数据维护，普通用户高效检索物品信息（含尺寸，单位毫米）。
- **Target Users**: 管理员（后台操作）、普通用户（前台查询）。

## Goals
- 管理员可维护物品、分类、账号、库存数量及流水。
- 普通用户可登录前台，按多条件检索并分页查看库存。
- 前后端分离的 REST API 设计，后续可被微信小程序复用。
- 权限严格隔离：普通用户无法触碰后台管理能力。

## Non-Goals
- 本期不做微信小程序端（仅保证 API 可复用，不在本期实现小程序页面）。
- 本期不做部署上线（本地跑通即可）。
- 本期不做采购/财务/多仓库/多租户。
- 本期不做 Excel 批量导入导出。
- 本期不做注册自助流程（账号由管理员创建）。
- 本期不做对象存储（图片存本地服务器）。

## Functional Requirements
- **FR-1 鉴权与角色**: 系统支持账号密码登录，区分「管理员」与「普通用户」两种角色；未登录不可访问任何业务页面/接口。
- **FR-2 账号管理（管理员）**: 管理员可创建、编辑、启用/禁用普通用户账号；普通用户不可管理账号。
- **FR-3 分类管理（管理员）**: 管理员可新增、编辑、删除、查看分类；被物品引用的分类不可直接删除（需提示）。
- **FR-4 物品管理（管理员）**: 管理员可上架物品，填写：名称、型号、分类、单图、单价、备注、供应商、内径(mm)、外径(mm)、高度(mm)、初始数量；可编辑、删除物品。
- **FR-5 出入库（管理员）**: 管理员可对物品执行入库/出库；操作后物品当前数量正确更新，并生成一条流水（含物品、方向、数量、操作人、时间）。
- **FR-6 流水查询（管理员）**: 管理员后台可查看历史出入库流水，支持按物品、时间范围筛选。
- **FR-7 前台查询（普通用户）**: 普通用户登录前台后，可按名称/型号模糊搜索、按分类筛选、按内径/外径/高度范围筛选，结果分页展示。
- **FR-8 前台可见字段**: 普通用户可见物品的名称、型号、分类、尺寸（内径/外径/高度）、当前数量、单价、图片、备注、供应商。
- **FR-9 图片**: 物品支持单图上传，存于本地服务器，前台可展示。
- **FR-10 权限隔离**: 普通用户无法访问后台页面，也无法调用任何后台写接口；直接访问被拒绝。

## Non-Functional Requirements
- **NFR-1 权限安全**: 所有管理类接口必须校验登录态与角色，未登录返回 401，普通用户返回 403。
- **NFR-2 数据一致性**: 出入库必须在单个事务中同时更新物品数量与写入流水，不允许出现数量已改但无流水或反之。
- **NFR-3 库存约束**: 出库数量不可超过物品当前库存。
- **NFR-4 API 可复用**: 后端提供 RESTful + JWT 鉴权的 API，不依赖浏览器 Cookie/Session，便于后续微信小程序调用。
- **NFR-5 本地运行**: 项目可在本地一键安装依赖并启动（PostgreSQL 需用户本地提供连接）。
- **NFR-6 分页性能**: 前台查询支持分页，避免一次性加载全部数据。

## Constraints
- **Technical**: Next.js（App Router）全栈；Prisma ORM；PostgreSQL；图片存本地文件系统。
- **Business**: 仅两种角色（管理员 / 普通用户）；账号由管理员创建，不开放自助注册。
- **Dependencies**: 本地需可用的 PostgreSQL 实例；Node.js 环境。

## Assumptions
- 用户本地已安装或可安装 PostgreSQL，并能提供连接串；若未安装，开发期可用 Docker 起一个本地 PostgreSQL。
- 尺寸字段为数值型（毫米），可包含小数；查询时按数值范围筛选。
- 初始需有一个默认管理员账号用于首次登录（种子数据）。
- 图片存储路径为项目本地目录，通过静态 URL 访问。

## Acceptance Criteria

### AC-1: 登录与角色路由隔离
- **Type**: `rule`
- **Given**: 系统存在管理员账号与普通用户账号
- **When**: 分别以管理员、普通用户登录，并尝试访问后台页面/接口
- **Then**: 管理员可进入后台；普通用户被重定向/限制在前台；未登录访问任意业务页/接口被拦截
- **Pass Condition**: 普通用户访问后台管理接口返回 403；未登录返回 401；管理员正常访问
- **Evidence**: 启动服务后用两个角色账号分别请求后台 API，观察 HTTP 状态码

### AC-2: 管理员可创建普通用户并可登录
- **Type**: `rule`
- **Given**: 管理员已登录后台
- **When**: 管理员创建一个普通用户账号（账号+密码）
- **Then**: 该新账号可在前台登录成功
- **Pass Condition**: 新建账号前台登录返回有效凭证并进入查询页
- **Evidence**: 调用创建账号 API 后用新账号登录前台

### AC-3: 分类 CRUD 与引用保护
- **Type**: `rule`
- **Given**: 管理员已登录
- **When**: 新增/编辑/删除分类；尝试删除一个已被物品引用的分类
- **Then**: 增删改生效；被引用的分类删除被拒绝并提示
- **Pass Condition**: 分类列表正确反映变更；删除被引用分类返回错误且分类仍存在
- **Evidence**: 调用分类 CRUD API 并验证数据库状态

### AC-4: 物品上架与字段完整性
- **Type**: `rule`
- **Given**: 管理员已登录且存在至少一个分类
- **When**: 管理员上架物品，填写名称、型号、分类、图片、单价、备注、供应商、内径、外径、高度、初始数量
- **Then**: 物品创建成功，字段完整保存，前台可查到该物品
- **Pass Condition**: 前台查询返回该物品且所有字段值正确
- **Evidence**: 上架后调用前台查询 API 验证字段

### AC-5: 物品编辑与删除
- **Type**: `rule`
- **Given**: 存在一个物品
- **When**: 管理员编辑该物品字段；或删除该物品
- **Then**: 编辑前台反映新值；删除后前台查不到
- **Pass Condition**: 编辑后查询返回更新值；删除后查询无此物品
- **Evidence**: 编辑/删除 API 后验证前台查询结果

### AC-6: 入库出库更新数量并生成流水
- **Type**: `rule`
- **Given**: 存在一个数量为 N 的物品
- **When**: 管理员对其入库 +X、出库 -Y（Y≤N+X）
- **Then**: 物品当前数量变为 N+X-Y；生成两条流水（入库+X、出库-Y），含操作人与时间
- **Pass Condition**: 数量计算正确；流水表存在对应两条记录
- **Evidence**: 出入库后查物品数量与流水列表

### AC-7: 出库不可超库存
- **Type**: `rule`
- **Given**: 物品当前数量为 N
- **When**: 管理员尝试出库 N+1
- **Then**: 操作被拒绝，数量不变，无流水产生
- **Pass Condition**: 接口返回错误；物品数量仍为 N；无新增流水
- **Evidence**: 调用超额出库 API 验证返回与数据状态

### AC-8: 出入库事务一致性
- **Type**: `rule`
- **Given**: 执行一次出入库操作
- **When**: 操作成功
- **Then**: 物品数量更新与流水写入同时成功或同时失败，不会出现只改数量无流水或只写流水未改数量
- **Pass Condition**: 数据库中数量与流水始终对应
- **Evidence**: 检查 Prisma 事务实现；多次出入库后核对数量=初始+入库总和-出库总和

### AC-9: 历史流水查询与筛选
- **Type**: `rule`
- **Given**: 存在若干出入库流水
- **When**: 管理员在后台查看流水，按物品、时间范围筛选
- **Then**: 返回符合条件的流水记录
- **Pass Condition**: 筛选结果与条件一致
- **Evidence**: 调用流水查询 API 带筛选参数验证

### AC-10: 前台多条件检索与分页
- **Type**: `rule`
- **Given**: 存在多条物品数据
- **When**: 普通用户在前台按名称/型号搜索、按分类筛选、按内径/外径/高度范围筛选，并翻页
- **Then**: 返回符合全部条件的结果，分页正确
- **Pass Condition**: 组合筛选结果正确；分页参数生效
- **Evidence**: 调用前台查询 API 组合参数验证返回条数与内容

### AC-11: 前台可见字段与权限边界
- **Type**: `rule`
- **Given**: 普通用户已登录
- **When**: 普通用户查看物品详情/列表，并尝试调用任意后台写接口（如上架、出入库、删分类）
- **Then**: 列表/详情可见名称、型号、分类、尺寸、数量、单价、图片、备注、供应商；调用后台写接口被拒绝（403）
- **Pass Condition**: 可见字段齐全且正确；写接口返回 403
- **Evidence**: 前台查询返回字段校验；普通用户 token 调用写接口验证 403

### AC-12: API 可复用于小程序
- **Type**: `rule`
- **Given**: 后端 API 已实现
- **When**: 用非浏览器客户端（如 curl/Postman）携带 JWT 调用查询与登录接口
- **Then**: 接口正常返回 JSON，不依赖 Cookie/Session
- **Pass Condition**: 纯 HTTP 客户端可完成登录与查询
- **Evidence**: curl 调用登录获取 token，再带 token 调用查询 API 成功

### AC-13: 代码结构与 API 设计质量
- **Type**: `rubric`
- **Dimension**: 前后端分离、模块化、RESTful API 设计清晰度，便于后续小程序复用
- **Scale**: 1-5
- **Anchors**: 1 = 前后端耦合混乱、API 不规则；3 = 基本可用但分层一般；5 = 清晰分层（页面/组件/API/服务/模型），API 规范统一、鉴权中间件集中
- **Pass Threshold**: >= 4
- **Evidence**: 审查项目目录结构与 API 路由组织

### AC-14: 前台查询与后台管理可用性
- **Type**: `rubric`
- **Dimension**: UI 操作流畅度与信息展示清晰度
- **Scale**: 1-5
- **Anchors**: 1 = 页面残缺、操作卡顿/报错；3 = 功能可用但交互粗糙；5 = 后台管理操作顺畅、前台查询筛选分页体验良好、字段展示清晰
- **Pass Threshold**: >= 4
- **Evidence**: 实际运行后人工浏览后台与前台各页面
